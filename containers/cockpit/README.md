# cockpit — web console (bastion mode)

A single-container Cockpit web service: the container form of
`ansible/playbooks/cockpit/`. The playbook installs the `cockpit`
metapackage on each host and enables `cockpit.socket`; this stack runs
the same web service (cockpit-ws, from the official
`quay.io/cockpit/ws` image, pinned at 368) as one hardened container
instead — same house style as the other stacks (cap_drop ALL,
read_only, no-new-privileges, resource limits, healthcheck).

## How the container model works here

Upstream builds this image to manage a host: its default deployment
(the image's own RUN label) is a privileged container with the host's
PID namespace and the host filesystem mounted at `/host`. This stack
deliberately does not do that. With no `/host` mount the image runs
in its unprivileged **bastion mode** (upstream's term): the console
serves the login page, the user names a host, and Cockpit connects to
that host over SSH using the user's own credentials for it. That is
the central-instance model `cockpit_setup.yml` already assumes ("your
central Cockpit instance should be able to gather performance data
from this host").

The host port is 9091 because the monitoring stack already publishes
9090 (Prometheus) when both stacks share a host; inside the container
the port stays Cockpit's native 9090.

## What this does not replace

The playbook stays the way hosts get their side of Cockpit:

- `cockpit_setup.yml` still installs the host packages, including the
  bridge the console talks to once connected. A host with no Cockpit
  packages can still be reached from this console in a limited form,
  but the full page set comes from the host's own install. PCP is not
  part of this repo's Cockpit setup by decision (2026-10-22): metric
  history lives in the monitoring stack (Prometheus/Grafana), so the
  console runs live-only and nothing here is containerized for it.

## 🛠️ Setup

There is no `.env` and there are no secrets to configure: this stack
holds no credentials. Authentication happens at login, with each
user's own account on the target host, over SSH.

1. Start the stack: `docker compose up -d`
1. Browse to `https://<host>:9091/`. The TLS certificate is
   self-signed (generated by the image on first start), so the
   browser warning is expected. To serve a real certificate instead,
   drop a `<name>.cert` / `<name>.key` pair into the `cockpit_certs`
   volume (mounted at `/etc/cockpit/ws-certs.d`) and restart.
1. Log in: fill in the **Connect to** field with a host that runs
   Cockpit (the playbook hosts), and your user name and password on
   that host. Confirm the SSH host key fingerprint the login page
   shows before accepting it, the same as any first SSH connection.

## ✅ Verification (canary)

1. `curl -k https://<host>:9091/login` returns 200 and the login
   page (titled "Cockpit Bastion").
1. Log in to a playbook-managed host and confirm its dashboard loads.
1. If that host also ran `cockpit_setup.yml`, open its Metrics page
   and confirm live graphs are updating — historical graphs are
   intentionally absent (no PCP, by the decision recorded above);
   metric history lives in the monitoring stack.

## Optional: manage the container's own host

If a box should be managed by a Cockpit running on itself, upstream's
model is a privileged container using the image's labels:

```bash
podman container runlabel --name cockpit-ws RUN quay.io/cockpit/ws:368
podman container runlabel INSTALL quay.io/cockpit/ws:368
systemctl enable cockpit.service
```

That deployment is privileged, shares the host PID namespace, and
mounts the host filesystem at `/host` — it replaces this stack's
hardening wholesale and is not part of it. The repo's existing way to
get host-local Cockpit remains `cockpit_setup.yml`.
